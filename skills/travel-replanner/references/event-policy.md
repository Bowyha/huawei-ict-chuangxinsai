# 事件与修正策略

| 事件kind | 输入关注点 | 推荐处理 |
|---|---|---|
| departure_delay | 当前时间、预计可出发时间、实际出发点 | 先算第一段路，顺延可选活动，保留固定时间 |
| weather | 具体日期时段、官方天气来源、受影响活动 | 选择附近适用替代活动；降雨不自动等于景区关闭 |
| place_unavailable | 景点、关闭/预约失败原因、生效时段 | 核实后移除该时段冲突，替换或改期 |
| preference | 用户明确不想去的地方、偏好 | 尽量保留原案，修改未开始的可选活动 |
| budget | 新预算口径、已支付支出、退改成本 | 同币种全程重算，不虚构退款或抹掉支出 |
| mobility | 步行上限、休息需求、允许交通 | 累计已走与剩余步行，不能只计算未来部分 |

event.status=confirmed/unknown；确认依据source_ids必须引用真实资料或用户明确请求。天气预报可作为已确认的预报资料，但应在说明中保留其预测性质。unknown事件要求查证或条件性规划，不能给出无条件ready。

可执行约束放在event.restrictions：blocked_place_ids明确整个剩余行程都不能访问的地点；blocked_windows用place_id/start/end明确仅某时段不可访问。不要把今天下午关闭误写成整个旅行都不能去。用户说“不想去”也可以转成明确的未来禁选条件。

纯自然语言描述不会自动被程序理解。天气/景点不可用事件若没有结构化限制或additional_checks，程序只返回partial；智能体必须先补齐受影响的地点、时段或可检验条件。偏好型软条件可以用文字解释取舍，不宣称已由代码验证。

## 冻结与当前锚点

基线由实际进度维护者提供；completed结束时间不晚于as_of；in_progress最多一个，必须已经开始；冻结活动应位于计划的连续前缀。planned即使开始时间已过去，也不自动改成completed，而是列为stale，等待重排。

in_progress的计划结束时间可能只是预测，ready_at必须至少为as_of及该结束时间中的较晚值；预测发生变化应先由上游更新带来源的基线，重规划器不自行改写它。已完成活动之间的历史交通逐字段冻结，不能改路程来抹掉已走步行或已花时间。

起点是当前用户提供的anchor_place_id；start_leg连接该锚点与候选第一个planned活动。若还有in_progress，则锚点应为其预计结束地点。即使同地也需明确duration=0及来源，不把未知当零。

当前锚点与最后冻结活动地点不同，应先在基线中补齐已发生移动记录（必要时建一个短的已完成到达活动），本模块返回partial等待状态补全，避免少算时间、距离和费用。不得偷偷使用旧起点。

## 确认规则

用户明确的新预算/每日时间窗/步行上限等由requirement_updates表示，confirmed=true须有用户请求引用；false时不应用，只标needs_confirmation。候选不能直接更改requirements来避开旧约束。

locked活动改变、mandatory地点替换、不可选活动删除、预约条款改变均按校验器标确认。历史记录被改写为blocked而不是确认后直接放行。订单取消、改签、退款和支付均不由本Skill执行。

每轮保留original_version和event.id；由宿主做版本一致性检查，用户接受前检测版本是否已被其他请求更新。guard无数据库，不提供持久化、原子更新或幂等存储。最多两轮后停止自动尝试，清楚展示未解决的约束。
